# 歌曲管理任务书

更新日期为 2026-11-17。本文记录管理员歌曲管理的整体流程、接口对应、已确认决定与分步交付边界。人类已审阅任务书及 MGMT-01 书面设计，授权编写管理列表实施计划。

## 目标与页面组织

管理员从业务侧栏进入歌曲管理，浏览全部歌曲状态，通过独立批量导入页创建草稿，再按需要编辑、发布、归档和彻底删除。管理能力依据本次登录的 ADMIN 身份判断，管理员以 USER 身份登录时遵循普通用户规则。

管理页面复用现有顶部栏、桌面侧栏、手机左抽屉和嫩叶绿视觉体系。管理对象为共享曲库中的歌曲，管理员可维护其他管理员创建的歌曲。[曲库任务书](library-homepage.md)与[列表权限契约](../api/track/list-tracks.md)

| 页面     | 设计地址                       | 职责                                       |
| -------- | ------------------------------ | ------------------------------------------ |
| 管理列表 | `/admin/tracks`                | 查询、状态筛选、排序、分页与已交付操作入口 |
| 批量导入 | `/admin/tracks/import`         | 多文件选择、逐首导入、进度、结果与恢复     |
| 草稿编辑 | `/admin/tracks/{trackId}/edit` | 读取当前草稿、修改元数据、保存与冲突恢复   |

这些地址是前端路由设计。生产路由和菜单随对应切片交付注册。管理模块内各页面归属同一“歌曲管理”导航项，从导入或编辑页返回列表时恢复原关键词、状态筛选、排序、页大小和页码。

## 状态与操作

| 当前状态  | 操作       | 成功结果                         |
| --------- | ---------- | -------------------------------- |
| 上传成功  | 创建草稿   | DRAFT，返回导入结果与元数据警告  |
| DRAFT     | 编辑并保存 | DRAFT，使用读取到的 version 提交 |
| DRAFT     | 发布       | PUBLISHED                        |
| DRAFT     | 归档       | ARCHIVED                         |
| PUBLISHED | 归档       | ARCHIVED                         |
| ARCHIVED  | 彻底删除   | 删除歌曲及关联媒体，返回 204     |

发布、归档和彻底删除使用二次确认，说明实际后果。操作依据歌曲 ID 发起，服务端执行状态与并发检查。成功后重新读取相关列表，冲突时读取最新状态后由管理员重新决定操作。

归档会保留歌曲资料和媒体，普通用户后续歌曲入口按状态过滤。彻底删除先清理媒体对象再删除数据库记录，导入历史保留。失败依据稳定错误码反馈并提供重试。再次删除返回 404 时提示歌曲已不存在并刷新列表。[发布契约](../api/track/publish-track.md)、[归档契约](../api/track/archive-track.md)与[删除契约](../api/track/delete-track.md)

## 接口地图

| 能力         | Method 与 Path                          | 关键消费规则                                                     | 契约                                           |
| ------------ | --------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------- |
| 管理列表     | GET `/api/v1/tracks`                    | ADMIN 省略 status 表示全部，或筛选单一状态，使用服务端分页和搜索 | [列表](../api/track/list-tracks.md)            |
| 当前歌曲资料 | GET `/api/v1/tracks/{trackId}`          | ADMIN 可读三种状态，编辑进入时重新读取当前资料                   | [详情](../api/track/get-track-detail.md)       |
| 导入         | POST `/api/v1/track-imports`            | multipart，uploadId 与单个 file，MP3／FLAC，每个文件最大 200 MiB | [导入](../api/track/import-track.md)           |
| 草稿更新     | PATCH `/api/v1/tracks/{trackId}/draft`  | DRAFT，version 必填，缺失字段保持原值，可空字段的 null 表示清空  | [草稿更新](../api/track/update-track-draft.md) |
| 发布         | POST `/api/v1/tracks/{trackId}/publish` | 无请求体，DRAFT 转 PUBLISHED，冲突后重读                         | [发布](../api/track/publish-track.md)          |
| 归档         | POST `/api/v1/tracks/{trackId}/archive` | 无请求体，DRAFT／PUBLISHED 转 ARCHIVED                           | [归档](../api/track/archive-track.md)          |
| 彻底删除     | DELETE `/api/v1/tracks/{trackId}`       | 无请求体，ARCHIVED，204 为成功结果                               | [删除](../api/track/delete-track.md)           |
| 鉴权封面     | GET `/api/v1/tracks/{trackId}/cover`    | 使用已知业务地址与 Bearer 请求头获取图片，失败使用缺省图         | [封面](../api/track/get-track-cover.md)        |

写接口均要求本次 ADMIN 身份。发布、归档请求采用服务端并发控制，编辑请求携带客户端读取的 version。业务请求经 `src/api/`，错误按 ProblemDetail 的稳定 code 处理，ID 与 Long 统计沿用已有精确解析方案。

## 批量导入流程

### 文件与处理结果

管理员选择多个文件，页面显示文件名、大小、文件校验反馈、逐文件进度及结果。选择与提交校验依据导入契约的格式和 200 MiB 限制，文件有效性由后端校验。前端每次发送一个文件，为每项生成独立 UUID uploadId。

文件发送到 100% 后显示“文件发送完成，正在处理”。后端还需校验音频、提取标签和内嵌封面、写入媒体及创建草稿，收到合法的首次 201 或幂等重放 200，且导入结果 status 为 READY 并携带可用歌曲结果后才显示成功。元数据警告与成功同时呈现，成功计数包含这些项目。

成功项保留返回的歌曲信息。草稿编辑切片交付后，进入编辑时重新读取当前状态和版本。批次完成后可前往草稿列表。标题／艺术家回退、文字截断、曲序／碟号异常等警告提示管理员核对资料，无封面及封面过大的警告使用缺省封面反馈。

### 重试与暂停

| 结果                             | 界面与调度行为                                                          |
| -------------------------------- | ----------------------------------------------------------------------- |
| 本地文件校验失败                 | 标记对应项，提供移除或重新选择入口，处理其他有效文件                    |
| 415 格式或 422 音频元数据错误    | 标记对应项及安全文案，继续下一项                                        |
| 200／201 且合法导入结果          | 保存该项结果，运行状态下继续下一项                                      |
| 超时、断网、异常响应             | 标记“导入结果待确认”，保留原文件和原 uploadId，暂停后续项并提供手动重试 |
| IMPORT_IN_PROGRESS               | 保留待确认项，提示稍后使用原文件与原 uploadId 重试，后续队列保持暂停    |
| IMPORT_CONFLICT                  | 展示导入标识冲突及该项上下文，暂停并由管理员处理                        |
| 429 TRACK_IMPORT_RATE_LIMITED    | 暂停并保留队列，按实际有效等待信息反馈，提供手动恢复                    |
| 503 媒体、导入存储或补偿清理故障 | 保留待确认项及安全错误提示，暂停后续项，恢复时使用原键与原文件          |
| 当前会话失效或身份变化           | 终止旧批次的本地调度，释放文件引用，按会话规则恢复导航                  |

相同 uploadId 的重放要求相同文件名与内容，后端通过 SHA-256 判定内容。重试沿用原 File、文件名与 uploadId，新选择的导入项获得自己的标识。批次状态、文件状态和服务器 READY 各有明确用途，界面只将已取得导入结果的项目计为成功。

导入契约已有 429 code，具体额度、窗口和 Retry-After 规则尚未给出。首版使用暂停与手动恢复，精确倒计时以有效契约为依据。请求中断或服务故障后的逐项结果，原键保留时通过原键与原文件重放确认。管理列表只提供已有歌曲的人工核对线索，导入项的关联结果以原返回结果或同键重放为依据。

### 切页与会话生命周期

批次由 Pinia 的导入业务状态及持续存在的调度逻辑持有，保存在当前标签页、当前 ADMIN 会话的内存中。站内切页保留 File 引用、uploadId、已完成结果和待处理项。

离开导入页时，先标记暂停后续调度，当前已发送请求继续取得成功、失败或结果待确认中的一个终态，随后保持暂停。返回导入页展示准确结果，等待管理员点击继续。批次提供完成当前项后暂停的操作，并说明当前项仍在处理。

刷新或关闭标签页会丢失内存中的文件引用、uploadId 与批次记录，页面明确提示本批次的内存生命周期。管理员可从管理列表人工查看已有歌曲，未取得可靠关联结果的原导入仍属待确认，重新选择文件属于新的导入意图。需要可靠逐项恢复时，以保留的原键与原文件重放为依据。

会话失效、退出或建立新会话时，清空旧批次的队列、结果与本地资源。每项发送前重新核对 ADMIN 会话与 revision，旧响应按原会话归属处理。

## 草稿编辑流程

编辑页展示当前封面与时长，提供歌名、艺术家、专辑、曲序和碟号表单。按当前有效草稿更新契约执行字段校验，提交携带读取时的 version，保存后使用响应中的最新版本。

仅提交发生变化的字段，可空字段被清空时显式提交 null。保存失败保留输入，未保存修改离页时提供保存、放弃或留在当前的选择。

当前 DRAFT 与服务端已保存资料一致时可发起发布，有未保存修改时先保存。保存与发布为独立动作，发布使用当前接口的确认与错误恢复流程。

版本冲突时保留本人输入并读取最新资料，展示差异供人工核对，确认后用最新版本再次保存。状态冲突后使用重新读取到的状态调整可用操作，资源不存在时提供返回管理列表的恢复入口。

### version 读取前置条件

现行 PATCH 强制 version，但当前列表、详情和导入响应文档均未提供其读取字段。MGMT-03 实施前需由后端契约提供方补齐有效读取规则。已确认的建议是在现有歌曲详情响应中增加当前 version，用于首次打开、重新进入和冲突恢复。具体类型、范围、可空性及角色消费规则以人类提供的新契约为准。

现有 API 文档作为只读依赖，本任务书记录消费需求和前置条件。管理列表、导入与已有状态操作可按各自契约独立推进。

## 验收与当前状态

通用验收覆盖当前 ADMIN 身份、普通 USER 导航与接口拒绝、401 会话失效、403 无权限、404、409、429、5xx、加载／空／错误、请求过期与取消、Long 精度和合法 null。批量导入另覆盖发送与处理阶段、逐项结果、原键重试、暂停调度与会话清理，编辑另覆盖字段缺失／null 与版本冲突。

运行逻辑切片按项目实际 scripts 完成安装、check、覆盖率及适用的 mock Playwright，逐文件完整行覆盖率至少 80%、分支至少 70%。代码任务各自记录真实命令、结果、失败与跳过。当前文档工作采用契约、范围、直接链接和一致性检查，业务运行验证在对应代码任务执行。

本轮已有 ADMIN 权限、编辑范围、批量方式、页面组织、列表规则、跨页暂停、编辑恢复和切片组织的人类确认。2026-11-17 人类通过书面方案并授权编写 [MGMT-01 实施计划](../superpowers/plans/2026-11-17-track-management-list.md)，人类随后通过计划并指定当前会话主 Agent 实施。MGMT-01 已完成实现、验证和独立审核。546 条单测、112 条端到端通过，逐文件覆盖率达标，Claude Code 第 1 轮实质审核结论为 accepted，其他切片保持待交付。[功能与验证](../features/track-management.md)及[独立审核报告](../reviews/2026-11-17-track-management-review.md)登记完整证据。
