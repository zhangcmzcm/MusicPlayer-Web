# 登录后续功能任务书

更新日期：2026-11-06。

## 用途与当前基线

本任务书汇总登录相关的后续功能、后端依赖、已有设计决策和实施边界，方便选取下一项任务。任务编号用于跟踪，不表示已授权开始实现；每次由人类选定一个切片，完成设计、实现、测试和独立审核。

登录切片已通过审核并推送。现有功能为邮箱密码、用户名密码、邮箱验证码登录，以及管理员本次身份选择；默认成功状态仍停留登录页，安全站内 redirect 回跳已具备。当前只有 `/login` 业务路由，没有注册或忘记密码假入口。

本次只新增任务文档，不修改代码、接口契约、主题规范或审核协议。接口准备情况按当前工作区 `docs/api/` 判断，不等于已经完成真实后端联调或部署验收。

## AUTH-01：注册与注册链接

### 接口与校验

- `POST /api/v1/auth/register`：[注册契约](../api/auth/register-user.md)。
- `POST /api/v1/email/send-code`，用途 `REGISTER`：[发送验证码契约](../api/email/send-code.md)。
- 用户名为 3–20 位 ASCII 字母、数字或下划线；不得套用登录用户名的 3–80 规则。
- 新注册密码为 8–72 个可打印 ASCII 字符（U+0020–U+007E），禁止全空格；保留首尾空格，不 trim、不截断、不预哈希，不额外要求字符种类组合。
- 邮箱在后端契约中可选；提供时必须配套验证码，不提供时验证码应为空或不传。正式表单是否采用邮箱注册主流程、是否提供无邮箱注册入口，实施前明确，不由构图样片决定。
- 注册响应不是登录会话，不擅自假定注册成功会自动登录。成功后的回登录、账号预填及 redirect 传递策略，实施前确认。

### 已确认的页面衔接

- `/login` 与未来 `/register` 为两个路由，共享持续存在的树叶场景；各自负责业务表单。
- 登录表单底部加入可用的注册链接；注册页具备返回登录入口。
- 桌面叶片左右各偏移 12%；登录叶脉右倾，注册翻面后左倾，叶尖仍朝上；注册侧文案位于左侧，使用竖排。叶片尺寸可按真实表单调整。
- 手机居中、小幅飘移翻面；支持减少动态设置、直接打开注册地址、浏览器返回及转场取消清理。
- 翻面随注册功能接入，不另建无业务用途的演示路由。

具体依据见[登录设计第 5、6 节](../superpowers/specs/2026-10-31-login-design.md)和[登录功能文档](../features/login.md)。已有决策直接复用；注册新增布局与交互语义仍需确认。

验收重点：注册成功、条件必填、密码字符与长度边界、验证码前导零、用户名／邮箱冲突、限流、防重复提交、导航与共享场景生命周期，以及现有登录回归。

## AUTH-02：找回密码与忘记密码链接

- 已有 `POST /api/v1/users/password-reset-requests`：[申请契约](../api/user/request-password-reset.md)。
- 仍缺最终确认验证码并设置新密码的接口。不能用需要有效登录及旧密码的 `PUT /users/me/password` 代替；最终请求、密码规则、成功后撤销与导航行为均以待补契约为准。
- 当前申请返回 `202`、`challengeId` 和 `expiresAt`；仅表示受理，不证明账户存在或邮件已发送。提示应保持一致，避免泄漏账号是否存在。
- challenge 临时保留用于后续确认，不写日志；验证码按字符串处理，保留前导零。
- 申请时不携带业务 Bearer；遵守 `Retry-After`，不借用登录验证码的 scope 语义；503 或响应丢失可能已有副作用，不自动无条件重试。
- 未绑定邮箱的账户暂不支持自助找回，不自行新增其他身份恢复渠道。
- 沿用已确认位置：密码框下方靠右显示“忘记密码？”，仅出现在密码登录方式；完整流程可用后再接入链接。

验收重点：最终契约补齐后，覆盖申请受理、统一提示、限流、申请与验证码失效、确认成功及失败恢复。确认接口未交付前，此任务保持待依赖状态。

## AUTH-03／04：当前资料与修改用户名

- `GET /api/v1/users/me`：[读取契约](../api/user/get-current-user.md)。
- `PATCH /api/v1/users/me`：[修改用户名契约](../api/user/update-current-user.md)。
- 建议先交付资料读取页面，再独立交付改名交互；具体入口与布局尚未确认。
- 资料响应中的 `userRole` 是账户最高角色，`loginRole` 是本次登录身份。可用操作依据本次身份，不能因账户为 ADMIN 而提升 USER 登录的操作权限。
- email、createdAt 按契约保留 null；时间展示显式处理时区。资料 DTO 与登录会话 DTO 不同，不能直接相互替换。
- 改名只发送 username，按 3–20 位 ASCII 字母、数字或下划线验证；处理大小写和唯一冲突。成功不撤销登录，应同步当前展示资料及必要的会话缓存，避免刷新后恢复旧用户名。
- 不将每次打开登录页都读取资料作为默认要求；请求时机随资料切片明确。

验收重点：本人读取、空邮箱／历史空创建时间、最高角色与登录身份不同、会话失效、存储失败；改名补充校验、大小写、同名、409 冲突和成功同步。

## AUTH-05：修改密码

- `PUT /api/v1/users/me/password`：[改密契约](../api/user/change-password.md)。
- 放在账户安全流程，不放进未登录的找回密码流程；页面入口与样式实施前确认。
- oldPassword 按本接口兼容历史密码规则处理，不套用新密码 ASCII／72 字符限制；newPassword 按本接口 8–72 个可打印 ASCII 字符等规则处理。原值保留，不 trim。
- 如使用确认密码字段，只作前端一致性校验，不发送给后端。
- 成功为 204，无新 Token；清理当前会话并引导重新登录，说明其他设备及角色的旧登录也会失效。
- 失败不自动重复提交；冲突、限流与未知结果恢复按本接口契约明确。

验收重点：历史原密码形态、新密码边界与原密码等价、错误旧密码、限流、防重复、204 成功退出及使用新密码重新登录。

## AUTH-06：再次验证与绑定／更换邮箱

### 接口依赖

| 步骤                           | 接口与契约                                                                                                     |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 向当前绑定邮箱发送再次验证邮件 | `POST /api/v1/users/me/reauthentication-email-requests`：[文档](../api/user/request-reauthentication-email.md) |
| 密码或专用邮箱码再次验证       | `POST /api/v1/users/me/reauthentications`：[文档](../api/user/reauthenticate-current-user.md)                  |
| 向新邮箱申请验证码             | `POST /api/v1/users/me/email-change-requests`：[文档](../api/user/request-email-change.md)                     |
| 确认绑定／变更邮箱             | `PUT /api/v1/users/me/email`：[文档](../api/user/confirm-email-change.md)                                      |

### 接入要求

- 首次绑定和换邮箱使用同一组邮箱变更接口；无当前邮箱时不能使用当前邮箱码再次验证，可使用密码方式。
- 再次验证邮件请求必须是零字节正文，不能发送 `{}`；专用 challenge 不能与 REGISTER、LOGIN 或新邮箱验证码混用。
- 再次验证成功只返回 Token、类型、到期时间和 authenticatedAt，没有 user；更新 Token 时保留已有用户资料及本次身份，不弹管理员身份选择、不提升权限。
- 由后端判断 300 秒近期资格，不从响应到达时重新计时，也不依赖前端解码 JWT 作为授权判断。
- `REAUTHENTICATION_REQUIRED`：保留当前登录、输入与申请，进入再次验证；验证成功后在原申请期限内继续原操作，不延长 challenge 有效期。
- `REAUTHENTICATION_FAILED`：保留原登录与验证交互，提示凭据失败。Token 本身过期、撤销或无效才恢复登录。
- **接入前必须调整统一 401 分流**：当前 HTTP 层对当前受保护会话的 401 一律通知退出，不能直接用于上述两类业务 401。继续保留旧会话迟到 401 不影响新会话的保护。
- 邮箱最终确认成功为 204，无新 Token；清会话并重新登录。503／回包丢失时结果可能已提交，不能只靠旧 Token 失效断言换邮箱成功，需恢复有效登录后读取资料核实。
- 新增邮件发送流程的服务端等待可达 20 秒，现有 HTTP 默认超时 15 秒；接入时评估针对接口的超时与结果未知提示，不顺手全局扩大超时。

该任务包含多段流程，开工前按可独立验收程度拆分；再次验证交互优先作为有实际消费方的必要组件交付，不建立无入口的组件或假安全页。失败恢复、有限重试、焦点与操作上下文的具体体验仍需确认。

验收重点：两种再次验证、无当前邮箱、近期资格不足、业务 401 不退出、真正失效退出、换 Token 后迟到响应、challenge 隔离与到期、邮件冲突／限流／未知结果及邮箱确认成功退出。

- 覆盖三种登录、两种管理员身份、刷新恢复及无权限目标的关联回归。

### AUTH-08：一次性凭据的异常恢复提示

完成记录为 `890c21a`／`0a30ff7`，布局稳定与异常恢复维护已获实现审核 accepted。后续手机一屏与浮动标签维护 `2f460de`／`ecfd5ee` 也已通过关联回归及独立审核。具体行为与验证见[登录功能文档](../features/login.md)。

## 建议实施顺序与待确认事项

1. 优先选择 AUTH-01，交付注册、注册链接及已确认的树叶转场。
2. AUTH-02 等待最终重置接口；契约齐全后可独立提前，不必等待账户中心。
3. 选择 AUTH-03，再按需求选择 AUTH-04、AUTH-05。
4. AUTH-06 在接口语义澄清后确认交互并拆分；401 分流与 Token 更新随实际消费方接入。
5. AUTH-07 随歌曲列表交付；AUTH-08 已完成。

以上是建议顺序，不是已批准排期。待确认内容包括注册是否提供无邮箱方式、注册成功后的导航与预填、账户页面入口与布局、找回最终契约及邮箱安全流程的切片划分。

已验收登录的遗留非阻断建议仅作参考：NOTE-002 手机叶片裁剪依赖可在相关视觉维护时评估；NOTE-006 展示字段异常的安全降级需要明确策略后再考虑，不默认夹入后续业务切片。
