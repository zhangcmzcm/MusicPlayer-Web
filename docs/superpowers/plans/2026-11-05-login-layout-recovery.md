# 登录页布局稳定与异常恢复实施计划

> 执行方式：沿用 Codex 实现、Claude 独立审核、人类最终确认的协作方式；本会话顺序实施，不自动创建子 Agent。执行阶段若使用计划执行技能，读取 `superpowers:executing-plans`；本文件目前仅为待人类审阅的计划，不授权提前实现。

**目标：** 保持登录叶片、表单与普通桌面页面高度稳定，并提供一次性登录凭据结果未知时的正确恢复引导。

**架构：** useLogin 维护页面私有恢复提示，保留原 ApiError；LoginView 负责稳定反馈和标题布局，LoginForm 负责字段及折叠区容量，AuthScene 负责视口、叶片与滚动降级。继续使用现有 auth store、HTTP、请求取消与限流机制，不修改认证契约或全局 401。

**技术栈：** Vue 3、纯 JavaScript、原生 scoped CSS、Element Plus 全量引入、Pinia、Vitest／Vue Test Utils、Playwright Chromium；不新增依赖或配置体系。

**设计依据：** [已 accepted 的设计](../specs/2026-11-05-login-layout-recovery-design.md)，设计提交 `eb3a53e885fe73498ebfd06339091dddd71aa962`。设计文档审阅第 1 轮已通过，实现任务独立计审核轮次。

## 全局约束

- 一个维护任务：布局稳定与异常恢复。注册、找回密码、翻面、资料、再次验证、真实新导航和全局 401 分流不在范围内。
- 普通桌面 CSS 视口：1366×768、1440×900、1920×1080；默认字号、100% 缩放下一屏容纳。小屏／矮窗口／字体放大允许整页滚动，不裁切文字、不在叶片内部滚动。
- 桌面中心左移 12%，输入和按钮水平对齐关系保留；仅登录标题组整体右移，管理员标题保持居中；嫩叶绿、身份白叶／淡绿叶、减少动态和焦点规则不变。
- 每字段预留两行错误；接口错误、恢复说明与验证码通知考虑并存；折叠区按完整展开占高保留；未来两行导航仅预留容量，不渲染假入口。
- 不更改登录的 8–128 字符密码规则，不套用注册新密码 ASCII／72 字符规则；不改 Token、权限或 Ticket 有效期。
- 再次提交、重新发码均由用户决定，不自动重试、不清空冷却截止时间；取消和迟到响应不能更新新状态。
- 四条最终验证命令实际运行；改动业务源码逐文件行 ≥80%、分支 ≥70%，纯样式变化说明替代验证。不以全仓平均代替文件级报告。
- 只提交明确文件，禁止 `git add .`。现有 API 文档、任务书及预览产物不混入实现提交；预览目录继续被忽略。

## 重点回归风险

1. 错误、恢复说明、发码通知并存导致超出预留高度：任务 1 验证语义可并存，任务 2 在最矮桌面验证几何与轮廓。
2. 已发请求失败晚到，覆盖重启或新请求提示：任务 1 用 deferred／AbortController 断言旧错误与恢复说明不能恢复。
3. 固定折叠高度后隐藏按钮仍可聚焦：任务 2 验证收起无可操作项，展开可键盘访问，切换后重新收起。
4. 1366×768 无滚动但标题／底部落到叶外：任务 2 检查整页尺寸与实际 SVG 轮廓，不能只验证元素存在或只看截图。
5. 普通视口正常而短屏、200% 放大被裁切：任务 2 验证整页滚动及焦点可达，任务 3 人工真实浏览器缩放，不以 deviceScaleFactor 替代。

## 任务 1：按请求阶段显示恢复引导

**文件：** 修改 `src/composables/useLogin.js`、`src/views/login/LoginView.vue`、`src/components/auth/RoleSelection.vue` 及前述两个 spec。

**接口：**

- `useLogin(auth)` 新增返回 `recoveryNotice: Ref<string>`，初始为空串。其余返回值与签名不变。
- 私有 `fail(failure, phase)`：phase 精确为 `PASSWORD`、`EMAIL_CODE`、`ROLE_SELECTION`；在发请求前捕获阶段，不在异步返回后猜测当前登录方式。
- LoginView 在原安全错误后显示恢复说明，使用稳定测试标识 `login-recovery`，同一区域只宣读一次，不另叠加重复 alert。原错误和说明均可阅读。
- RoleSelection 新增 `restartRecommended: Boolean`，默认 false；当身份选择出现恢复说明时为 true，只强调现有 `restart-login`，不隐藏角色或自动消费／删除票据。

- [ ] **步骤 1：补分类与原错误保留测试。** 在 useLogin.spec 复用现有 setup、valid、ticket 工厂，分别参数化 NETWORK_ERROR、TIMEOUT、503：EMAIL_CODE 应包含「验证码可能已被使用」，ROLE_SELECTION 应包含「登录票据也可能已失效」；断言 `flow.error.value` 仍为原 ApiError、pending 解除、只发一次请求、未发验证码。密码登录同类失败提示为空。
- [ ] **步骤 2：补负例与清理测试。** 按设计 §5.1 的其余类别验证：401 INVALID_CREDENTIALS、LOGIN_TICKET_INVALID、403、429、客户端／存储异常无附加说明，取消静默；发码失败无凭据消费说明。deferred 请求在重启或卸载后拒绝，不能恢复旧提示；新操作开始、切换方式和成功清理提示。验证码恢复后发码仍受原冷却控制。
