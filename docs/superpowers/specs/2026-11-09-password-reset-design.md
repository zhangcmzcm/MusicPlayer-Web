# 找回密码页面设计

日期为 2026-11-09。本文记录本次对话逐节确认的 AUTH-02 前端布局、交互、职责与验收范围，供书面审阅。

## 1. 目标、状态与交付边界

提供邮箱找回密码流程、密码登录方式下的“忘记密码？”入口，以及成功回登录的邮箱预填和提示。

用户已确认居中留白方案 A、桌面与手机统一顶部两步进度，以及独立验证码校验通过后进入设置新密码。操作顺序包括输入邮箱、验证邮箱验证码、设置新密码三个阶段，前两个阶段归入顶部的“验证邮箱”。

本次提交为设计文档。完整实施的前置条件为后端票据改密契约已交付且与独立验证码校验接口衔接一致。前端设计的书面确认与后端接口的交付状态分别记录。

范围外包括注册、登录共享树叶场景改版、账户中心、已登录用户主动改密、邮箱变更、其他身份恢复渠道、依赖升级和全局 HTTP 重构。

## 2. 权威资料与实施前置条件

### 2.1 已提供契约

- [申请找回密码验证码](../../api/user/request-password-reset.md)规定公开 `POST /api/v1/users/password-reset-requests`。请求使用真实邮箱，202 返回 challengeId 和 expiresAt，仅表示受理。
- [独立验证找回密码验证码](../../api/user/verify-password-reset.md)规定公开 `POST /api/v1/users/password-reset-verifications`。请求使用 challengeId 和 code，200 返回 resetTicket 和 expiresAt。成功兑换消费旧验证码并签发一次性设置密码资格。
- [当前重置密码契约](../../api/user/confirm-password-reset.md)仍规定 `POST /api/v1/users/password-resets` 接收 challengeId、code、newPassword，并返回 204。
- [登录后续任务书 AUTH-02](../../tasks/login-follow-up.md)提供单切片边界、密码登录下的入口位置和公开请求要求。其中“缺少验证码确认接口”的历史状态已由新增独立校验契约部分替代，最终票据改密契约仍是实施依赖。

### 2.2 当前接口交付边界

独立校验文档明确要求第三步 resetTicket/newPassword 改造审核通过后整体切换。独立校验已经消费旧验证码，现有组合改密请求无法继续使用该验证码完成下一步。

后端需要提供票据改密的正式请求、成功响应、错误码、额度与 Retry-After、票据过期或被替换、密码相同、票据消费时机，以及网络或服务异常后的恢复语义。前端依据正式契约补齐第三步字段与决策表，再进入完整功能的实施计划。

本文第二步“设置新密码”的界面表达用户已确认的目标流程。resetTicket 是已提供独立校验契约中的正式字段，最终提交请求及业务错误分支需由票据改密契约落实。当前接口缺口作为明确实施前置条件保留，避免把设计草图误认为可联调实现。

### 2.3 视觉与工程依据

配色与气质引用[主题规范](../../design/theme.md)及[视觉样例](../../../example/index.html)。本页面采用本次用户确认的独立布局。

技术栈沿用 Vue 3、JavaScript、Vue Router、Pinia、Axios、Element Plus、Vitest 与 Playwright，样式沿用原生 scoped CSS。认证、错误映射、安全站内回跳及敏感信息保护遵循项目现行协议。

## 3. 页面布局与视觉

已比较居中留白、浅绿页眉和细线表单框三个方案，用户选择 A 居中留白。

- 页面使用白色或浅暖白背景，主要绿色为既有嫩叶绿与动作绿。顶部进度、主按钮、链接和少量品牌元素承担主题色。
- 页眉左侧为“风与叶”品牌，右侧为“返回登录”。主体居中，桌面表单宽约 410px，手机随视口缩放并保留左右留白。
- 表单顶部统一显示“1 验证邮箱 → 2 设置新密码”。当前步骤使用绿色实心圆，完成步骤显示完成标记，下一步使用浅色描边圆。
- 标题使用现有系统衬线字体，正文和表单使用现有系统无衬线字体。输入采用上方可见标签、浅色边线，主按钮使用绿色。
- 验证码使用单个六位输入框，旁边提供重新获取入口。新密码和确认密码使用密码输入及显隐控制。
- 页脚使用“一叶清新　一曲自在”。排版和颜色参考本次确认的居中留白草图，具体间距与响应式 CSS 在该方向内自主调整。
- 320×740、390×844 为常规手机检查尺寸，同时检查桌面 1366×768、1440×900、1920×1080。长错误、极矮视口、放大和软键盘展开时采用自然纵向滚动，保证字段、按钮和导航可达。

桌面与手机的进度位置相同。页面通过普通导航进入独立场景，步骤切换聚焦当前标题，减少动态偏好沿用既有规则。

## 4. 路由、入口与页面状态

### 4.1 路由与入口

新增独立懒加载路由 `/forgot-password`，页面独立于现有 AuthScene 叶片容器。

登录页 EMAIL_PASSWORD 与 USERNAME_PASSWORD 方式在密码框下方靠右提供“忘记密码？”。邮箱验证码登录继续使用该方式原有交互。页面右上角“返回登录”用于普通返回。

已有安全 redirect 可以随找回导航保留，回登录后由既有安全回跳逻辑处理。找回密码路由归入认证流程，作为登录后 redirect 目标时应被排除。

同一路由内维护三个表单阶段，URL 保持业务导航信息。邮箱、验证码、challengeId、resetTicket 与密码保存在内存中。

### 4.2 初始邮箱输入

默认打开“找回密码”，顶部第 1 步激活。用户输入账号绑定的完整邮箱，点击“获取验证码”。

邮箱按申请契约 trim 并规范化为小写，检查合法单邮箱及最多 120 字符。请求体仅携带 email。未绑定邮箱账号暂不支持自助找回，页面提供统一说明。

申请受理后暂存规范化邮箱、challengeId 与 expiresAt，进入同一步骤内的验证码输入状态。脱敏邮箱仅作界面展示，请求使用完整规范化邮箱。

### 4.3 验证码输入

顶部仍为第 1 步。显示脱敏邮箱、“修改邮箱”、六位验证码输入框、“重新获取”和“验证并继续”。

受理提示使用“若该邮箱已绑定账号，你将收到验证码”，统一表达账户存在与邮件送达的不确定性。

code 按六位 ASCII 数字字符串处理，保留前导零及原值。用户主动提交时调用独立校验接口，使用当前 challengeId 与 code。仅收到合法有效的成功票据后进入顶部第 2 步。

用户点击“修改邮箱”返回邮箱输入状态，清除旧验证码和申请信息，重新点击获取后才发起新申请。重新获取成功后使用新申请响应，旧请求的迟到结果通过操作序号与取消机制隔离。

### 4.4 设置新密码

顶部第 1 步显示完成，第 2 步激活。表单只需新密码与确认新密码，提供“重置密码”和“重新验证邮箱”入口。

确认密码仅用于前端一致性校验。当前密码输入设计沿用已提供密码规则，即 8–72 位可打印 ASCII、非全空格、保留首尾空格；实施时须与最终票据改密契约核对。

验证成功后设置密码的期限使用独立校验响应中新的 expiresAt。邮箱申请的到期时间与设置密码票据的到期时间分别管理。重新验证入口清理当前流程凭据和敏感输入，回到邮箱输入阶段，由用户主动申请。

## 5. 状态、错误与恢复

| 场景                   | 页面行为                                                                                    | 依据                                         |
| ---------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 本地校验失败           | 对应字段显示安全文案，定位首个错误，保留可修改输入                                          | API 请求规则与已确认表单行为                 |
| 申请、验证或重置提交中 | 显示加载，禁用本次流程编辑与重复操作，保留离开页面的导航能力                                | 客户端运行规则                               |
| 申请 202               | 切换验证码输入，统一展示条件式邮件提示                                                      | 申请契约的受理成功语义                       |
| 申请限流               | 按 Retry-After 显示等待与禁用，找回用途独立管理期限                                         | 申请契约的邮箱及 IP 限流                     |
| 申请服务或网络结果未知 | 提示申请结果暂未确认，允许用户在等待后主动恢复                                              | 申请契约的副作用与恢复语义                   |
| 验证码统一验证失败     | 保留输入，提示检查或重新申请，不展示剩余尝试次数                                            | 独立校验契约及本次用户确认                   |
| 校验限流               | 按 PASSWORD_RESET_VERIFICATION_RATE_LIMITED 与 Retry-After 呈现等待，统一失败仍使用统一文案 | 独立校验契约的额度与错误归属                 |
| 校验服务或网络结果未知 | 提示验证结果暂未确认，引导重新申请验证码                                                    | 独立校验契约的消费与故障恢复                 |
| 票据已知过期           | 清除有效设置密码资格，显示重新验证邮箱入口                                                  | 独立校验契约的 expiresAt 与本次用户确认      |
| 刷新、离开或卸载       | 清理申请、验证码、票据和密码，取消客户端等待并隔离迟到响应；再次进入从邮箱输入开始          | 本次用户确认与客户端生命周期                 |
| 最终重置成功           | 回登录，切换邮箱密码方式，预填本次邮箱，密码留空，显示成功提示并消费一次性交接              | 本次用户确认；成功条件需引用最终票据改密契约 |

错误依据稳定 code 映射，未知错误走统一安全反馈。主动取消与过期响应静默处理。请求取消只结束客户端等待，服务端可能已执行的副作用依各接口契约恢复。

申请与校验的限流属于找回用途，按各自契约管理，重新申请和页面切换继续服从服务端额度。限流信息与流程凭据分开保存。原申请或校验响应形态异常时按结果未知路径恢复，避免把已执行的操作表现为确定未执行。

最终重置的失败分类、密码相同后的票据状态、提交未知后的会话清理与恢复，均列入第 2 节的正式契约核对项。该依赖补齐后追加对应决策表。

## 6. 权限、敏感信息与会话

申请和验证码校验均为公开接口，使用现有 publicRequest 封装。USER 与 ADMIN 使用同一流程，资源目标由后端绑定决定。

完整邮箱用于申请与成功回登录预填。challengeId、code、resetTicket 和密码仅用于内存中的当前流程；日志与持久化存储只沿用项目允许的非敏感配置。验证码校验成功后清理已消费的验证码与申请标识，保留设置密码所需的票据、期限和登录交接所需邮箱。

最终票据改密成功时的旧会话处理以正式契约落实，状态修改经过 auth store。迟到的旧操作结果应与当前会话和流程代际核对，防止影响后来建立的新会话。

成功交接仅向登录页传递邮箱与成功提示，用完清除。密码由用户在登录页重新输入，管理员继续沿用现有身份选择流程。

## 8. 验收范围

- 邮箱输入、验证码获取与独立校验、设置新密码、回登录预填构成完整 happy path，使用三个业务接口的 mock 验证参数、响应与界面结果。
- 覆盖邮箱格式和 120 字符边界、验证码前导零及非法形态、新密码边界和确认密码一致性。最终提交体按新契约逐项断言。
- 覆盖合法与异常 challengeId／resetTicket／expiresAt、申请和票据各自过期、相同或不同邮箱重新申请、修改邮箱及取消后的迟到响应。
- 覆盖 pending 防重复、找回独立冷却、429 Retry-After、统一验证失败、申请与校验结果未知，以及最终改密契约允许的失败与恢复。
- 覆盖刷新、离开、卸载、普通回登录、成功交接仅消费一次，以及安全 redirect 的保留与认证流程排除。
- 检查桌面与手机顶部两步进度、错误文案可达性、密码显隐、键盘操作、标题焦点、减少动态及窄屏纵向滚动。
- 登录三种方式、管理员身份选择、注册及相关会话回归继续运行。
- 实施交付执行现行 npm ci、check、Vitest 覆盖率和 Playwright 命令。逐个修改业务逻辑文件按完整文件口径核对行至少 80%、分支至少 70%，纯声明或展示文件逐项说明替代验证。

当前草图的 14 种状态检查仅验证预览的初始邮箱入口、桌面／手机状态切换与错误反馈展示。真实后端、邮件送达、跨浏览器和物理手机体验须在实施与联调阶段分别记录。
